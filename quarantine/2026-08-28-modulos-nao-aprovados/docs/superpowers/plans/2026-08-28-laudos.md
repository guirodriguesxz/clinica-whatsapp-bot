# Laudos/relatório de atendimento — Implementation Plan

Baseado em [2026-08-28-laudos-design.md](../specs/2026-08-28-laudos-design.md).
Sub-projeto 5 de 9. Mesmo padrão de execução dos sub-projetos anteriores:
TDD (`node --test`, `pool.query` mockado, sem Postgres real), uma migration
nova (não aplicada automaticamente — requer confirmação explícita do
usuário antes de rodar no Neon de produção).

## Global Constraints

- Sem banco de dev separado do de produção — a migration `013_laudos.sql`
  fica pronta mas **não é aplicada** por este plano. Só roda depois que o
  usuário confirmar.
- PDF gerado em memória (`Buffer`), nunca salvo em disco/banco — mesmo
  request/response cycle.
- Sem envio por e-mail, sem identidade visual, sem CPF/data de nascimento,
  sem histórico de laudos — tudo já descartado no spec.
- Nova dependência: `pdfkit` (já instalada em `package.json`).
- Mesma convenção de rotas origem-específica (`/presenca/agendamento/:id/...`
  vs `/presenca/importado/:id/...`) e mesmo padrão de motivo estruturado
  (`nao_encontrado`, `sem_observacao`) já usado em `registrarPresenca*` e
  `registrarPagamento*`.

## Task 1 — Migration `013_laudos.sql`

Só adiciona a coluna opcional, retroativa:

```sql
ALTER TABLE registros_atendimento
  ADD COLUMN IF NOT EXISTS profissional_responsavel TEXT;
```

Com o mesmo cabeçalho de aviso das migrations anteriores (011, 012) sobre
não aplicar sem confirmação.

## Task 2 — `registroAtendimentoModel.js`: persistir `profissional_responsavel`

- `buscarItensBot`/`buscarItensImportados`: adicionar
  `ra.profissional_responsavel` ao SELECT, pra pré-preencher o campo no
  formulário de `/presenca` (mesmo padrão de `ra.observacao_sessao`).
- `registrarPresencaBot`/`registrarPresencaImportado`: aceitar
  `profissionalResponsavel` (normalizado como `string | null`, igual
  `observacaoSessao`) e incluir no INSERT/UPSERT (`ON CONFLICT ... DO UPDATE
  SET profissional_responsavel = EXCLUDED.profissional_responsavel`).
- Testes: atualizar os mocks de `registrarPresencaBot`/`Importado` pra passar
  `profissionalResponsavel` e verificar que o parâmetro chega no INSERT;
  regressão pros testes existentes que já checam a query completa
  (`assert.match`) — confirmar que a coluna nova não quebra o número de
  placeholders (`$1`..`$5`).

## Task 3 — `laudoModel.js` (novo)

Busca os dados do laudo nas duas origens. Motivo estruturado, mesmo padrão
de `registrarPresenca*`:

- `nao_encontrado` — agendamento/importado não existe (404 no controller).
- `sem_observacao` — existe mas `observacao_sessao` é nula/vazia (400 no
  controller).
- Caminho feliz: `{ dados: { pacienteNome, data, profissionalResponsavel,
  observacaoSessao } }`.

```js
export async function buscarDadosLaudoBot(agendamentoId) { ... }
export async function buscarDadosLaudoImportado(agendamentoImportadoId) { ... }
```

- `buscarDadosLaudoBot`: `agendamentos JOIN pacientes LEFT JOIN
  registros_atendimento`, `profissionalResponsavel` = `ra.profissional_responsavel`
  direto (sem fallback — spec diz "campo simplesmente não aparece" pro bot).
- `buscarDadosLaudoImportado`: `agendamentos_importados LEFT JOIN
  registros_atendimento`, `profissionalResponsavel` = `ra.profissional_responsavel
  ?? ai.atendente ?? null` (fallback pro dado legado do sistema de agenda anterior).
- Testes: `nao_encontrado` (query vazia), `sem_observacao`
  (`observacao_sessao` null), caminho feliz nas duas origens, fallback
  `profissional_responsavel` ausente → usa `atendente`, e os dois ausentes →
  `profissionalResponsavel: null`.

## Task 4 — `laudoPdfService.js` (novo)

Duas funções exportadas — separar a decisão de "quais linhas de texto
aparecem" da renderização em pdfkit, porque pdfkit não expõe um jeito simples
de inspecionar o que já foi escrito antes de finalizar o documento (mesmo
problema citado no spec — "decidir no plano de implementação"). A decisão:
extrair `linhasCabecalhoLaudo(dados)` como função pura, testável direto
(sem tocar em pdfkit/PDF), e reservar o teste de `gerarPdfLaudo` pra um
smoke test único que só confirma que o PDF real foi gerado.

```js
// pura, sem I/O — decide o que entra no cabeçalho de dados (Paciente,
// Data, Profissional responsável — este último condicional)
export function linhasCabecalhoLaudo({ pacienteNome, data, profissionalResponsavel }) { ... }

// gera o PDF de verdade (pdfkit), devolve Promise<Buffer>
export function gerarPdfLaudo(dados) { ... }
```

- Testes de `linhasCabecalhoLaudo`: inclui a linha "Profissional responsável"
  quando presente; omite quando `null`/`undefined`/string vazia.
- Teste de `gerarPdfLaudo`: smoke test real (sem mock — geração pura em
  memória) checando que o `Buffer` começa com `%PDF` e tem tamanho > 0.

## Task 5 — Controller (`gerarLaudoBot`, `gerarLaudoImportado`)

- `idValido` já existe em `dashboardController.js` (financeiro) — mover pro
  topo do arquivo como helper compartilhado em vez de reimplementar um
  terceiro parser de id.
- Nome de arquivo: sanitizar o nome do paciente pra um slug ASCII (remover
  acentos, só `[a-z0-9-]`) antes de usar em `Content-Disposition` — um nome
  com acento/aspas quebraria o header HTTP.
- Fluxo: 404 se `idValido` falhar ou motivo `nao_encontrado`; 400 se motivo
  `sem_observacao`; senão gera o PDF e responde com
  `Content-Type: application/pdf` +
  `Content-Disposition: attachment; filename="laudo-<slug>-<data>.pdf"`.
- Testes: fluxo feliz nas duas origens (headers corretos, corpo é o Buffer
  do PDF), 404 pra id inválido/inexistente, 400 pra sem observação.

## Task 6 — Rotas

```js
router.get(
  "/presenca/agendamento/:id/laudo",
  asyncHandler(exigirLogin),
  asyncHandler(gerarLaudoBot)
);
router.get(
  "/presenca/importado/:id/laudo",
  asyncHandler(exigirLogin),
  asyncHandler(gerarLaudoImportado)
);
```

GET puro (download), sem `exigirCsrf` — mesmo padrão de `/financeiro` e
`/financeiro/relatorio`.

## Task 7 — View (`presenca/lista.ejs`)

- Adicionar `<input type="text" name="profissional_responsavel">` no
  formulário existente, pré-preenchido com `item.profissional_responsavel`.
- Adicionar link condicional "Gerar laudo" (`<a href="...">`, não precisa de
  form/CSRF por ser GET) visível só quando `item.observacao_sessao` estiver
  preenchida, apontando pra
  `/presenca/<agendamento|importado>/<id>/laudo` conforme `item.origem`.
